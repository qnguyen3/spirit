Phase 5 — Terminal input

Typing from the browser: raw keystrokes and paste into the PTY, a command composer at the shell prompt that keeps the desktop's blocks clean, an agent composer that reuses the rich-input submit strategies, signals (Ctrl-C / Ctrl-D), and the phone key toolbar with soft-keyboard handling.

Goal

From a phone: answer a Claude Code permission prompt ("1", Enter), type into vim, send a multi-line prompt to an agent through its rich input, run git status at the shell prompt and see it appear as a proper block on the desktop, paste a snippet, and interrupt a runaway command — all with a toolbar that makes Esc, Tab, Ctrl, arrows and Enter reachable above the soft keyboard.

Prerequisites

Phases 1–4. D8 defines which path each kind of input takes.

Tasks

Task 1 — Input commands and binary input frames (Rust)

  • terminal.input {terminal_id, bytes} and the binary input frame ([attach_id][bytes], resolved to the attachment's terminal) both call bridge.write_input(terminal_id, bytes, ctx): resolve the view; if model.is_read_only() → terminal_read_only; else terminal_view.update(ctx, |v, ctx| v.write_viewer_bytes_to_pty(bytes, ctx)). Cap MAX_INPUT_FRAME_BYTES; per-connection token bucket MAX_INPUT_BYTES_PER_SECOND (excess → rate_limited result for commands, dropped with a single log::warn! for binary frames). Binary input frames coalesce on the socket side (drain everything available, then one spawn) to avoid one main-thread hop per keystroke during fast typing.
  • terminal.paste {terminal_id, text}: mirror TerminalView::paste — add pub(crate) fn paste_text(&mut self, text: &str, ctx) on TerminalView that factors the existing body (view.rs:7618-7694) so the desktop and remote share one implementation (the desktop passes clipboard text, the remote passes the message text). Cap MAX_PASTE_BYTES.
  • terminal.run_command {terminal_id, text}: only when the terminal's mode is Prompt (recompute under the lock; do not trust the client's view) → execute_command_or_set_pending(text); else not_at_prompt. Reject embedded newlines unless the shell supports multi-line commands through the same path (it does — bytes_to_execute_command wraps in bracketed paste — so allow them but cap at MAX_PASTE_BYTES).
  • terminal.agent_submit / terminal.agent_insert: require CLIAgentSessionsModel::session(terminal_id) to exist → submit_cli_agent_rich_input / insert_text_into_cli_agent_input; else no_agent_session. When the session exists but input_state == Closed, agent_submit still works (the strategies write to the PTY) — that is the desktop's behavior too.
  • terminal.signal {terminal_id, signal}: interrupt → [0x03], eof → [0x04], through write_viewer_bytes_to_pty so Ctrl-C cancellation tracking (cli_agent_sessions/mod.rs:485) keeps working.
  • Tests commands_tests.rs: read-only refusal; run_command in running mode → not_at_prompt; agent_submit without a session → no_agent_session; token bucket refuses the 65th KiB in a second.

Task 2 — xterm input wiring (terminal.js)

  • Enable stdin: term.onData(str) → UTF-8 → binary input frame; term.onBinary(str) → bytes (latin1) → frame. Intercept paste (term.attachCustomKeyEventHandler for Ctrl/Cmd+V is not enough on mobile; listen to the paste event on term.textarea, preventDefault, send terminal.paste).
  • Focus management: tapping the terminal focuses term.textarea (opens the keyboard on mobile); a "Keyboard" toggle in the header focuses/blurs explicitly; Esc from the toolbar does not blur.
  • Local echo is never used; latency is the round trip (fine on LAN).

Task 3 — Composers (ui/terminal_view.js)

  • Command composer (mode prompt): single-line input with history (last 50 commands per terminal in memory), Enter or Run → terminal.run_command; on not_at_prompt (race with a program starting) fall back to a toast and keep the text. Shows the cwd basename as a prefix chip.
  • Agent composer (a live agent session on this terminal, regardless of input_open): multi-line textarea (auto-grow to 5 lines), Send → terminal.agent_submit; a hint row explains the !/& mode prefixes the desktop supports; "Insert without sending" secondary action → terminal.agent_insert. The desktop's draft text (draft_text) is not synchronized (out of scope).
  • Raw line (mode running without an agent session, or alt_screen): a single-line input whose Send writes the text plus \r as raw bytes — for programs that read lines (read, REPLs). Hidden by default under a "Type a line…" disclosure so the xterm textarea remains the primary input.
  • Composer choice is driven by the state snapshot (TerminalSummary.mode, agent) and updates live; the xterm keyboard input remains available in every mode.

Task 4 — Key toolbar (keys.js, ui/terminal_view.js)

  • Keys and bytes: Esc 1b, Tab 09, Enter 0d, Backspace 7f, ↑↓←→ (CSI A/B/D/C, or SS3 variants when the terminal reported APP_CURSOR — track DECSET ?1 from the stream on the client, or simply ask xterm: it exposes term.modes.applicationCursorKeysMode), Home/End, PgUp/PgDn, Ctrl (sticky: next key is sent as key & 0x1f — implement by injecting the control byte for the next onData character), Alt (sticky: prefix 1b), Ctrl+C and Ctrl+D shortcuts → terminal.signal, F1–F12 in an overflow group, and a "symbols" group (/ - | ~ \ : ' " ` ^ $). Long-press on arrows repeats at 60 ms.
  • Layout: horizontally scrollable, two rows on phones (the second row collapsible), single row on tablet/desktop; docked above the keyboard (visualViewport tracking on iOS: set the toolbar's bottom offset to window.innerHeight - visualViewport.height - visualViewport.offsetTop).
  • Haptic tick on key press where navigator.vibrate exists; visual pressed state; sticky modifiers render highlighted until consumed.

Task 5 — Desktop awareness

  • When remote input arrives on a terminal, the desktop shows a one-shot toast per terminal per session: "Remote device is typing in <tab title>" (throttled: at most once per 10 minutes per terminal) so a user at the desk is not surprised. Implement in bridge.write_input via ToastStack::add_ephemeral_toast on the owning window.

Out of scope

  • Mouse reporting from the phone (touch → SGR mouse events) — xterm.js can do it, but it is confusing on touch; add later behind a toggle. IME composition edge cases beyond what xterm handles. Syncing agent draft text. Kitty keyboard protocol encoding.

Verification

  • ./script/presubmit green; new command tests pass.
  • Phone: at the prompt, run echo hi from the composer → the desktop shows a new block with the command and output, the phone's xterm shows the echoed output; press Ctrl+C on a running sleep 100 → block cancelled on the desktop; in vim, navigate with arrows, insert text, Esc :wq from the toolbar; in a Claude Code permission prompt, press "1"/Enter and the agent proceeds; type a two-line prompt in the agent composer and Send → the agent receives it exactly once (compare with the desktop's rich input behavior for the same agent: Codex bracketed-paste, Claude delayed Enter).
  • Paste 5 KB of text into a running cat → arrives intact; paste into the composer at the prompt → becomes the command text.
  • iOS Safari: the toolbar stays visible above the keyboard in portrait and landscape; rotating keeps the fit; the page never scrolls the xterm out of view.
  • Two clients typing simultaneously interleave without losing bytes; the desktop toast appears once.
  • Rate limit: a script blasting 1 MB of input in a second is throttled and the desktop stays responsive.

Gotchas

  • Mode races: the phone may still show the command composer while the desktop already started a program. The server re-derives the mode under the lock and answers not_at_prompt; the client must keep the text and re-render when the next state arrives.
  • Never call write_viewer_bytes_to_pty while holding the model lock. The read-only check locks; drop the guard first (the desktop's own view.rs:3565-3568 exists precisely because of this deadlock).
  • Bracketed paste is decided server-side from needs_bracketed_paste(); the client must not wrap text itself, or programs receive doubled markers.
  • Enter is \r, not \n, everywhere on the PTY path (xterm already sends \r; the raw line and toolbar must too).
  • Ctrl as a sticky modifier must be applied before xterm's own encoding: capture the next onData character, replace it with the control byte, and cancel the original. Easiest: on sticky Ctrl, set a flag; in the onData handler, if the flag is set and the data is a single ASCII letter, send code & 0x1f instead.
  • Soft keyboards and xterm: Android's GBoard sends composition events; xterm handles them, but the raw line input must have autocapitalize="off" autocorrect="off" spellcheck="false" and inputmode="text"; the command composer likewise.
  • Do not add a "submit to input editor" path. The desktop's input editor is the desktop user's; remote commands execute directly so the two never fight over one buffer.
