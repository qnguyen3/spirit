Remote Control — Web UI Guide

How the browser client is built: files, state, networking, layouts per device, components, theming, the xterm.js viewer, mobile rules, and the design language. Phases 3–9 build it incrementally; this page is the shared contract so each phase adds to one coherent app instead of five.

Principles

  1. Mirror, don't reinvent. The web UI shows the same structure the desktop shows (Workspaces → Worktree sections → tabs → panes; Sessions ranked needs-input first) with the same names and status colors. Users should recognize the desktop in it.
  2. One screen at a time on phones. Every feature must work at 360×640 CSS px with the soft keyboard open. Tablet and laptop layouts add columns; they never add features.
  3. Server truth, thin client. The store is a verbatim copy of the last state snapshot plus connection/UI state (route, attached terminal, sheets). No optimistic mutation: commands are sent, the UI shows a pending indicator, the next state renders the result.
  4. No build step, no framework, no network. ES2020 modules loaded directly by the browser, a hand-written h() DOM helper, vendored xterm.js, everything served by Spirit (D12). No external fonts (system font stack; monospace stack for the terminal).
  5. Safe by construction. App strings go through textContent/h() only; the CSP forbids inline scripts, so there is no inline onclick anywhere; links to the desktop are commands, not URLs.

State & networking

store = {
  connection: { status: 'connecting'|'open'|'closed', instanceId, clientId, lastError, reconnectAt },
  hello: { protocol, appVersion, capabilities:Set, limits },
  snapshot: AppSnapshot | null,          // verbatim from the last state message
  version: number,
  route: { name, params },
  terminal: { attachId, terminalId, mode, cols, rows, pendingResync },
  ui: { sheet: null|{kind, props}, toasts: [], pendingCommands: Map, unread: { needsInput: number }, deviceLabel },
  prefs: { fontScale, sound, vibrate }   // localStorage, per device
}
  • ws.js owns the socket. command(name, params, {timeoutMs}) returns a Promise resolved by the matching result. Binary frames are demuxed by attach_id to a registered handler (the xterm instance). event messages fan out through a tiny emitter.
  • Reconnect: 0.5 s → 1 → 2 → 4 → 8 s with ±20 % jitter; a banner shows "Reconnecting…"; on reconnect with the same instance_id, re-attach the current terminal; with a different one, navigate to #/workspaces and toast "Spirit restarted".
  • Rendering is a full re-render of the active screen on every store change, using keyed DOM reuse only where it matters (the tab list and the xterm container, which must never be recreated while attached). This is fast at this data size; do not introduce a virtual DOM.

Screens

Workspaces (#/workspaces)

Cards from snapshot.projects (MRU order) preceded by a Home card. Card: name, kind icon, primary branch, "N worktrees", agent counters (working / needs attention) as colored pills, "open on desktop" indicator when open_in_window_id is set, last opened relative time. Tap → project.open then route to #/w/<id>. Long-press / kebab → Rename, Reveal, Remove (Phase 8). A "New Workspace" card opens the creation sheet (Phase 8). When features.ade_workspaces is false, only Home is shown and the copy explains why.

Workspace detail (#/w/<project_id> or #/w/home)

Header: name, branch, switch-to-desktop button. Body: sections[] rendered like the vertical tabs panel — section header (worktree name, branch chip, agent dot, "+" menu: New Terminal / Launch agent ▸ / Rename / Delete), then tab rows (kind icon with status dot, title, pane count, active highlight). Tapping a tab: tab.activate and route to its focused terminal (#/t/<terminal_id>) if it has one, else show the pane list. Tab row kebab: Close (confirm). Footer button: New Worktree (Phase 6). If the project is not open on the desktop, a banner offers "Open on desktop" (it will also open automatically when creating anything inside it).

Sessions (#/sessions)

Two groups: Live (from snapshot.sessions, ranked needs-input → failed → working → idle/done) and History (Phase 7, from history.list). Live row: agent icon (brand color), status pill, title (latest prompt), workspace · worktree, tool preview; tap → terminal; secondary: Show on desktop. History row: agent, title, cwd basename, relative time, message count; actions: Resume, Copy command.

Terminal (#/t/<terminal_id>)

Header: back, tab title · agent name, mode badge (prompt = "shell", running = "running", alt_screen = "full screen"), connection dot, kebab (Show on desktop, Font size, Detach). Body: the xterm container. Bottom: contextual input area (Phase 5): at the prompt a command composer (single line, Run); while running, the key toolbar plus a raw-input line; when an agent session has input open, the agent composer (multi-line, Send, mode prefixes hint) with the agent context strip above it (tool name / summary / status, Phase 7).

Components (all in styles.css + ui/*.js)

  • Card, Row (icon · texts · trailing), StatusDot (idle grey, working blue pulse, needs-attention amber, failed red, done green — same semantics as ConversationStatus), Pill, Badge.
  • Sheet (bottom sheet on phone, dialog elsewhere) with title, body, primary/secondary actions; traps focus; closes on Esc/backdrop; used for New Worktree, Launch Agent, Confirm, New Workspace, Directory picker.
  • Menu (kebab/long-press) rendered as a sheet on phone and a popover elsewhere.
  • Toast stack (bottom, above nav), auto-dismiss 4 s, errors persist until tapped.
  • Banner (top of content): connection state, LAN-without-TLS warning, needs-input alert (with Open button).
  • Composer: textarea that grows to 5 lines, Enter sends (Shift+Enter newline) on desktop; on phones a Send button (Enter inserts newline for the agent composer, sends for the command composer).
  • KeyToolbar: horizontally scrollable row of key buttons; Ctrl/Alt are sticky modifiers applied to the next key; long-press repeats arrows.
  • DirPicker (Phase 8): breadcrumb + list + "Use this folder".

Theming

CSS custom properties on :root, dark by default (Spirit's default look) with a light theme under @media (prefers-color-scheme: light) and a manual override stored in prefs (data-theme on <html>). Tokens: --bg, --bg-elev, --fg, --fg-muted, --border, --accent, --ok, --warn, --danger, --info, radii (6/10/16), spacing scale (4-based), --font-ui (system stack), --font-mono (ui-monospace, SF Mono, Menlo, Consolas, "DejaVu Sans Mono", monospace). The xterm theme object is derived from the same tokens plus the standard 16 ANSI colors in Spirit's default dark/light palettes (copy the values from the bundled default themes under app/assets/bundled; if none maps cleanly, use the Warp default theme values hard-coded in terminal.js). Agent brand colors come from the snapshot (brand_color).

Terminal viewer (terminal.js)

  • One Terminal instance for the currently viewed terminal; created lazily, disposed on navigation away (after terminal.detach). Options: cols/rows from the attach result, scrollback: 5000, allowProposedApi: false, convertEol: false, cursorBlink: true, macOptionIsMeta: true, fontFamily: var(--font-mono), theme from tokens, disableStdin until Phase 5. Renderer: default DOM renderer (the WebGL addon is not vendored in v1).
  • Applying a snapshot: term.reset() then term.write(bytes) (Uint8Array from base64). The server composes history + \r\n×rows + live screen + cursor + modes; the client does nothing clever.
  • Fit rule (D9): cols/rows are fixed to the desktop's. After each layout change (ResizeObserver on the container, visualViewport resize on mobile), compute the largest font size in [8, 20] px such that cols × cellWidth ≤ containerWidth; if the result is under 8 px, keep 8 px and enable horizontal scrolling of the container. Row overflow scrolls vertically inside the container. Never call term.resize with different cols/rows than the server's.
  • Binary I/O: output frames → term.write(uint8); batch consecutive frames within one animation frame. Input (Phase 5): term.onData(str) → UTF-8 encode → binary frame; term.onBinary likewise. Paste in the terminal: intercept and send terminal.paste so the server decides on bracketed paste.
  • Resync: on terminal.resync apply the snapshot; on terminal.closed show "This terminal was closed" with a back button. When the snapshot's mode/cols/rows for the attached terminal change in a state message, update the header badge and refit; the server also sends a resync on size change.
  • Mode-driven chrome: prompt → command composer, toolbar hidden; running → toolbar + raw line; alt_screen → toolbar only; agent input_open → agent composer replaces the raw line.

Mobile rules

  • Viewport meta: width=device-width, initial-scale=1, viewport-fit=cover, interactive-widget=resizes-content. Do not disable pinch zoom globally; the terminal container sets touch-action: pan-x pan-y.
  • Keyboard: focusing xterm's hidden textarea opens the soft keyboard; the key toolbar is position: sticky; bottom: 0 inside the terminal screen so it rides above the keyboard; on iOS use visualViewport to keep it visible. Blur on "Done".
  • Clipboard: navigator.clipboard is unavailable on plain-HTTP LAN origins; the Paste button opens a small sheet with a textarea the user pastes into, then sends terminal.paste. Copy uses term.getSelection() plus a "Copy" sheet showing the text for manual copy when the API is unavailable.
  • Touch targets ≥ 44 px; long-press = 500 ms with haptic (navigator.vibrate(10) when available); avoid hover-only affordances — every kebab is visible.
  • Back button: routes are hash-based so the OS back gesture navigates; sheets push a history entry so back closes them.
  • Battery: when document.hidden, detach the terminal after 30 s and stop rendering; re-attach on visibility.

Accessibility & quality bar

  • All controls are real <button>/<a> elements with labels; status dots carry aria-label; sheets use role="dialog" and aria-modal; live-region for toasts.
  • Color contrast ≥ 4.5:1 for text; status conveyed by icon + text, never color alone.
  • Performance budget: first paint < 1 s over LAN; JS excluding vendor < 150 KB unminified; a state message re-render < 16 ms for 200 tabs; xterm stays responsive at 5 MB/s output (drop to resync rather than queue).
  • Manual test devices for every phase that touches UI: iPhone (Safari), Android (Chrome), iPad, macOS Safari + Chrome. Record findings in the phase's verification notes.

Vendoring script — script/vendor_remote_control_assets

#!/bin/bash
set -euo pipefail
cd "$(dirname "$0")/../app/assets/web/remote_control/vendor"
fetch() { curl -fsSL "$1" -o "$2"; echo "$3  $2" | shasum -a 256 -c -; }
fetch https://cdn.jsdelivr.net/npm/@xterm/xterm@5.5.0/lib/xterm.js            xterm.js            <sha256>
fetch https://cdn.jsdelivr.net/npm/@xterm/xterm@5.5.0/css/xterm.css           xterm.css           <sha256>
fetch https://cdn.jsdelivr.net/npm/@xterm/addon-fit@0.10.0/lib/addon-fit.js   addon-fit.js        <sha256>
fetch https://cdn.jsdelivr.net/npm/@xterm/addon-web-links@0.11.0/lib/addon-web-links.js addon-web-links.js <sha256>

The implementer fills in the SHA-256 values on first download and commits both the script and the files. xterm.js ships UMD builds that define globals (window.Terminal, window.FitAddon); load them with classic <script> tags before the module script, since the CSP allows same-origin scripts. Record the exact versions in vendor/VERSIONS. License files (MIT) are committed alongside.
