Spirit — Remote Control

Master plan for Remote Control: a toggle in Settings that starts a local web server inside the running Spirit app and serves a responsive web UI (phone, tablet, laptop) that mirrors the desktop — see and type into any terminal, switch Workspaces, create Worktrees, launch and answer CLI agents, open new terminals — using the same models and actions the desktop UI uses.

How to use this spec

This directory contains one HTML file per phase plus three reference pages. Phases are ordered and each phase must leave the tree compiling and presubmit-green (./script/presubmit) — every phase is an independently landable unit of work. An implementing agent should read this overview fully, then protocol.html and web-ui.html, then execute the phase files in order. Every phase file has: Goal, Prerequisites, Context (with file:line references), Tasks, Out of scope, Verification, and Gotchas.

Line numbers were captured on 2026-09-07 at Spirit commit 606b9c2a (branch feat-remote-control) — treat them as strong hints, not gospel; re-locate symbols by name if a file has drifted.

The product in one page

The user flips Settings → Remote Control → Enable. Spirit starts an HTTP+WebSocket server bound to 127.0.0.1:7777 (port configurable) and shows the URL, a copy button, an "Open in browser" button and an access token. Opening the pairing URL in any browser sets a session cookie and loads a single-page web app that shows, live:

  • Workspaces (code name Project): cards with name, primary branch, worktree count, agent activity counters; tap to switch the desktop to that Workspace and open it in the web UI.
  • A Workspace's tabs, grouped into Worktree sections exactly like the desktop's vertical tabs panel (registry order, Primary first), each tab with its panes, titles, cwd, and agent status dot.
  • Any terminal: a faithful live mirror (xterm.js fed by the PTY byte stream) with a command composer at the shell prompt, an "agent composer" when a CLI agent is waiting for input, and a phone-friendly key toolbar (Esc, Tab, Ctrl, arrows, Enter…) while a program is running.
  • Sessions: every live CLI agent session ranked needs-input first, plus the on-disk session history with one-tap resume.
  • Creation: new terminal in a Worktree, launch an agent in a Worktree (with approval mode), create a Worktree (optionally with an agent), close tabs, delete Worktrees (dirty-checked), add/clone/create Workspaces.

It works adaptively on phones (bottom navigation, one screen at a time, key toolbar above the soft keyboard), tablets (sidebar + content) and laptops (three-column). Turning on "Allow access from other devices on this network" binds the server to all interfaces and shows a QR code with the LAN pairing URL; the recommended path for remote access is Tailscale or an SSH port-forward (no TLS in v1).

What this buys

Kick off three agents in three Worktrees at the desk, walk away, and answer their permission prompts from a phone; glance at what a long build printed from the couch; open a Workspace and start a terminal on the laptop from a tablet — all against the same live processes, with the desktop window updating in lockstep.

The most important fact: the control server already exists

app/src/local_control/ is an axum loopback HTTP server that already drives the UI

Gated by FeatureFlag::WarpControlCli, it owns a private tokio runtime, binds an ephemeral loopback port, routes POST /v1/control into a main-thread LocalControlBridge via ModelSpawner, and executes ~70 typed actions (tab create/activate/close, pane split/focus, input insert, settings, themes) with a security-reviewed credential broker. Read app/src/local_control/mod.rs:1-58 (architecture doc), mod.rs:184-260 (start), mod.rs:527-535 (the tokio→main-thread handoff), bridge.rs:41-190 (dispatch), resolver.rs (selectors → handles), handlers/app_state.rs (mutations) and specs/warp-control-cli/SECURITY.md before writing a line.

Remote Control copies its mechanics but is a separate module (D1). Its surface is the wrong shape for a browser: it rejects every request carrying an Origin header (mod.rs:652-684), issues single-action 5-minute grants through a Unix socket, has no push channel, no WebSocket, no terminal output, no Project/Worktree actions, and its resolver takes the first Workspace in a window (resolver.rs:228-241), which WorkspaceRegistry's own doc calls ambiguous now that a window hosts one Workspace per Project. Leave local_control untouched; do not extend its ActionKind catalog.

Key mechanics inherited from the existing codebase

  • Main-thread boundary: App is Rc<RefCell<AppContext>> (crates/warpui_core/src/core/app.rs:72), not Send. The only sanctioned bridge is ModelSpawner<M> (crates/warpui_core/src/core/model/context.rs:657-691): ctx.spawner() on the main thread, then spawner.spawn(move |model, ctx| …).await from any thread returns a value. Precedent: app/src/local_control/mod.rs:229-233, 527-535. There is no AsyncAppContext and no global tokio Handle.
  • Terminal I/O: the PTY reader fans raw bytes out through async_broadcast (crates/warp_terminal/src/event_listener.rs:86-96, created deactivated at app/src/terminal/local_tty/terminal_manager.rs:293-296); PtyRecorder (app/src/terminal/recorder.rs:143, 200-228) is the precedent consumer via activate_cloned(). Writes go through TerminalView::write_viewer_bytes_to_pty (app/src/terminal/view.rs:3796) and commands through execute_command_or_set_pending (view.rs:7142).
  • Terminal state: not one grid — a block list plus an alt screen (app/src/terminal/model/terminal_model.rs:349-382). is_input_box_visible (view.rs:3399) is the desktop's own "at the prompt" predicate; the remote mode derives from it (D8). Cells: crates/warp_terminal/src/model/grid/cell.rs:145; unified row accessor GridHandler::row (grid_handler.rs:2416); cursor cursor_render_point (:1650); DECSET state via ModeProvider/TermMode (crates/warp_terminal/src/model/mode.rs).
  • Size: the GUI layout owns the PTY size and re-sends it on every layout pass (app/src/terminal/terminal_size_element.rs:36-45); there is no arbiter. Hence D9: the browser follows the desktop's cols×rows.
  • Enumerating live UI: WorkspaceRegistry::all_workspaces (app/src/workspace/registry.rs:162) → workspace.tabs → tab.pane_group → visible_pane_ids / terminal_view_from_pane_id (app/src/pane_group/mod.rs:2148, 3999); precedent status_item::resolve_session (app/src/status_item.rs:194-216). Tab id = tab.pane_group.id(); there is no TabData.title — derive from PaneGroup::custom_title and pane summaries as Local Control does (app/src/local_control/handlers/metadata.rs:396-419).
  • Projects/Worktrees: ProjectRegistryModel (app/src/projects/registry.rs), ProjectHost screens and ProjectHostAction (app/src/projects/host.rs:117-195), creation/deletion pipelines on Workspace (app/src/workspace/view/worktrees.rs:183, 480, 545, 622), agent launch (app/src/workspace/view.rs:9246, 9323, catalog app/src/agent_launcher/catalog.rs:42).
  • Agent sessions: CLIAgentSessionsModel keyed by terminal view id (app/src/terminal/cli_agent_sessions/mod.rs:294-324), statuses at :27, events at :218; answers to permission prompts are raw PTY bytes; the rich-input submit strategies live in app/src/terminal/view/cli_agent_footer.rs:637-895.
  • Settings, flags, palette, tray, pill: toggleable-setting end-to-end precedent is alias_expansion_enabled (def app/src/settings/alias_expansion.rs, widget app/src/settings_view/features_page.rs:4966, palette pair :388-401, context flag app/src/workspace/view.rs:15538); secure setting precedent app/src/settings/local_control.rs; page registration app/src/settings_view/mod.rs:185-271, 933-943, 1020-1107, 1543-1551; tray app/src/status_item.rs:82-100; pill app/src/workspace/view.rs:4176-4256, 13851-13913.
  • Assets: rust-embed over app/assets (crates/warp_assets/src/lib.rs:7-18, build.rs); adding #[include = "web/**"] ships a web directory inside the binary; mime_guess and qrcode are already workspace dependencies (Cargo.toml:176, 208; qrcode is declared in app/Cargo.toml:155 and unused today).
  • Dependencies present: axum 0.8.4 (without the ws feature), hyper 1.x, tokio 1.47 (no workspace-level features — declare your own), tower-http 0.6 (only trace,cors enabled by crates/http_server), rand, base64, uuid, sha2. Absent: any WebSocket server, tokio-tungstenite (arrives with axum/ws), include_dir, mDNS/if-addrs crates.

Standing decisions

Resolved while planning; implementers follow them unless the repo owner overrides.

IDDecisionResolution
D1Relationship to Local ControlSeparate module app/src/remote_control/ and crate crates/remote_control, copying the mechanics of local_control (private runtime, ModelSpawner bridge, settings-driven lifecycle, resolver-style helpers) but with its own router, auth, protocol and handlers. local_control stays untouched. Shared code is limited to WarpUI/settings framework APIs.
D2RuntimeA private tokio::runtime::Runtime per server (new_multi_thread().worker_threads(2).enable_all()) owned by RemoteControlServer and dropped on stop, giving instant teardown of every connection. Not the app's Background executor (avoid coupling the app's executor to socket lifetimes), and note crates/http_server's runtime lacks enable_time(), which this server needs for heartbeats and coalescing.
D3Bind address and port127.0.0.1:<port>, default port 7777, setting remote_control.port. With remote_control.allow_lan_access = true bind 0.0.0.0:<port> (IPv4 only in v1). Bind failure → state Failed, toast, Settings shows the error; no automatic port hunting.
D4AuthenticationOne long-lived 256-bit random access token (base64url, generated on first enable, rotatable), stored as a SecureSetting (keychain / private store, never in settings.toml, never logged, never synced). Pairing = GET /pair?t=<token> (or a form POST) → server sets an HttpOnly; SameSite=Strict; Path=/ cookie spirit_rc holding a random session id, and 303-redirects to / so the token never stays in the address bar. Sessions persist across app restarts as SHA-256 hashes in a private setting so phones stay paired; rotation or disable revokes all. Authorization: Bearer <token> is also accepted on /api/* for curl/tests.
D5Browser hardeningHost allow-list (loopback names + LAN addresses when enabled) → else 421 (DNS-rebinding defence). WebSocket upgrades and all mutating requests require Origin == http://<Host>; mutating REST additionally requires header X-Spirit-Remote: 1. No CORS headers are ever emitted. Served HTML carries a strict CSP (default-src 'self'; connect-src 'self' ws:; img-src 'self' data:; style-src 'self'; script-src 'self'), X-Frame-Options: DENY, Referrer-Policy: no-referrer; API responses Cache-Control: no-store. Text from the app (titles, cwd, commands) is rendered via textContent, never HTML.
D6Transport securityPlain HTTP in v1. Loopback needs no TLS; LAN mode shows a persistent warning in Settings and in the web UI and recommends Tailscale (bind LAN, reach it over the tailnet) or ssh -L 7777:127.0.0.1:7777. Self-signed TLS with a pairing-time certificate pin is future work.
D7Wire protocolJSON text frames for control (hello, state, command/result, event, ping/pong) and binary frames for terminal bytes ([attach_id: u32 LE][bytes…]). State is pushed as full snapshots with a monotonically increasing version; diffs are future work (snapshots are tens of KB at most). All types live in crates/remote_control::protocol with PROTOCOL_VERSION; the client refuses a mismatched major. See protocol.html.
D8Terminal mirroringRelay the raw PTY byte stream into xterm.js (like ttyd/gotty), seeded on attach by an ANSI attach snapshot built server-side: recent block history as styled text, then the live screen (alt-screen grid or the active block's output grid) serialized by a new grid_to_ansi, then DECSET modes. No cell-diff protocol, no block-list renderer in the browser. The terminal's mode (prompt / running / alt_screen) is derived from is_input_box_visible + is_alt_screen_active and drives input routing and the mobile toolbar: at the prompt, commands are submitted through execute_command_or_set_pending so the desktop keeps clean blocks; while running, raw bytes go to the PTY; when a CLI agent session has its rich input open, text is submitted through submit_cli_agent_rich_input.
D9Terminal sizeThe desktop is authoritative. The web client renders exactly the desktop's cols×rows and scales its font (min 8px) or scrolls horizontally to fit; desktop resizes propagate as state changes. No remote-driven resize in v1 (there is no size arbiter — terminal_size_element.rs:36-45 re-sends the GUI size every layout). A "smallest client wins" arbiter is future work.
D10Identity on the wireproject_id/worktree_id are UUID strings (add Serialize/Deserialize to WorktreeId). window_id, screen_id (Workspace view id), tab_id (pane group id), pane_id, terminal_id (TerminalView id) are opaque decimal strings valid for one app process; hello.instance_id changes on restart and the client discards everything it knows. Format ids exactly as app/src/local_control/handlers/metadata.rs does.
D11Feature flag and channelsFeatureFlag::RemoteControl mirrors AdeWorkspaces exactly: cargo feature remote_control = [] in app/Cargo.toml listed in default, mapped in enabled_features() (app/src/features.rs:248), also in DOGFOOD_FLAGS. (The Oss channel is not dogfood — crates/warp_core/src/channel/mod.rs:30-35 — so DOGFOOD_FLAGS alone would not enable it.) The server is instantiated only for LaunchMode::App; the module is #[cfg(not(target_family = "wasm"))] because axum is.
D12Web client technologyHand-written ES2020 modules + CSS, no bundler, no framework, no Node in the build. Vendored, pinned @xterm/xterm 5.5.0 (+ @xterm/addon-fit, @xterm/addon-web-links) committed under app/assets/web/remote_control/vendor/ by a checked-in script with URLs and SHA-256 pins. Everything is embedded through crates/warp_assets and served by the Rust server; the page loads nothing from the network. Rationale: cargo bundle stays self-contained and the only JS precedent in-tree (crates/command-signatures-v2/js, yarn+tsc in build.rs) makes Node a soft build requirement that this feature must not make hard.
D13Change detectionThe bridge marks itself dirty from: ctx.observe on every registered Workspace view and every TerminalView it has seen, PaneGroupFocusEvents, ProjectRegistryEvents, CLIAgentSessionsModelEvents, and a 1 Hz reconcile timer while ≥1 client is connected. Rebuilds are coalesced (50 ms), compared structurally (PartialEq), and broadcast only when changed. No new WorkspaceEvent variants are required (WorkspaceEvent has only two today — app/src/workspace/view.rs:818).
D14Command executionEvery command runs on the main thread inside bridge_spawner.spawn, resolving handles through WorkspaceRegistry/ProjectRegistryModel and calling existing methods or handle_action(&WorkspaceAction::…) directly (Local Control's pattern, app/src/local_control/handlers/app_state.rs:361-370). Never string global actions. Where today's entry point is private and modal-bound (start_worktree_creation, execute_worktree_deletion, start_clone, start_create), refactor it into a headless pub(crate) function with a completion callback that the modal also calls — one code path.
D15Multiple clientsUp to 8 concurrent WebSocket clients per instance; all see the same state; input is shared (like a tmux session). The desktop pill shows the connected count.
D16Destructive commandsworktree.delete, tab.close, project.remove require "confirm": true; the web UI shows a confirmation sheet; dirty worktrees additionally require "force": true after a worktree.dirty_check. Nothing else is destructive.
D17Notifications on the deviceNo Web Push (service workers need a secure context; LAN IPs are not one). Needs-input alerts are in-page: banner, document.title badge, navigator.vibrate, optional beep — only while the page is open.
D18PersistenceNo SQLite changes. Public settings in settings.toml under remote_control.*; the token and paired-device hashes in private/secure storage.
D19LoggingTokens, session ids and cookies never reach logs; use safe_info!/safe_warn! (crates/warp_core/src/safe_log.rs) for anything that could contain them. Connects, disconnects, pairing successes/failures (remote address only) are logged at info.
D20Pane splits and layout editingOut of scope for v1 (the pane tree is displayed, focus works, no split/resize/move from the web). Local Control already has pane.split; adding it later is a handler and a button.

Global rules for every phase

  1. Green per phase: ./script/presubmit passes at the end of each phase. Use ./script/format, not plain cargo fmt.
  2. Zero comments in code. CLAUDE.md bans all comments in written/edited code (sole exception: a hidden constraint that would make a future reader break the code). Before reporting a phase done, run git diff and check added lines for //, /*, #, *. This applies to JavaScript and CSS too — no JSDoc, no // narration; a clear function name beats a comment.
  3. Feature flag: everything user-visible is gated by FeatureFlag::RemoteControl.is_enabled(); prefer runtime checks over #[cfg]. Flag off must be byte-identical to today: no settings group registered, no page, no pill, no tray entry, no listener.
  4. Main-thread boundary: code that touches AppContext, views, models, or TerminalModel runs only inside bridge_spawner.spawn(...) or in bridge callbacks. Tokio tasks hold only Send data (ModelSpawner, channels, async_broadcast receivers, Arc<Vec<u8>>). Never block the main thread on the network; never block_on from the bridge.
  5. TerminalModel locking: take model.lock() for the shortest possible scope, copy what you need out, drop it, then emit/notify/write. Never hold it across ctx.emit, ctx.notify, any update, a PTY write, or an .await. Never call a function that may lock while holding the lock.
  6. Bounded everything: every channel between tokio and the bridge or a client has a capacity and a documented overflow policy (drop + resync for terminal bytes, error for commands). Message size caps live in crates/remote_control::limits and are enforced server-side.
  7. Exhaustive matches: no wildcard _ arms where avoidable. CommandName, ServerMessage, ClientMessage, ServerState, TerminalMode are enums that must produce compile errors at consumers when extended.
  8. Style rules that will bite: ctx param named ctx and last (closure param is the exception); delete unused params entirely (never _-prefix); tests in sibling ${filename}_tests.rs files included via #[cfg(test)] #[path] mod tests;; banned APIs: std::process::Command → command::blocking::Command/command::r#async::Command, std::time::Instant → instant::Instant; inline format args; no Itertools::format in log macros; imports at the top of the file.
  9. Typed actions only: new desktop actions go on WorkspaceAction / page action enums. No new global string actions (app/src/workspace/global_actions.rs:20-21 is deprecated) — the tray's status_item:* handlers are the one place a string action already exists and may gain siblings for tray entries only.
  10. Security invariants are code, not docs: every route except /health, /pair and /assets/* goes through the auth extractor; every response goes through the security-headers layer; the Host check runs before routing. Add a test for each invariant in app/src/remote_control/mod_tests.rs (precedent: app/src/local_control/mod_tests.rs spins up a runtime and issues real HTTP requests).
  11. Web client rules: ES modules only, no innerHTML with app-provided strings, no external network requests, no build step, no framework, vendored files only from the pinned script, works with JavaScript features supported by Safari 16 / Chrome 110 (the oldest targets), and every screen must be usable at 360×640 CSS px.
  12. Keep commits reviewable: within a phase, separate additive scaffolding, refactors of existing code paths, and behavioral edits into distinct commits.
