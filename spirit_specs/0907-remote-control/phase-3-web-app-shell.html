Phase 3 — Web app shell

The responsive single-page app: store, WebSocket client, hash router, three device layouts, and the Workspaces / Workspace detail / Sessions / Terminal-placeholder screens rendering the live snapshot, plus the first navigation commands (open project, activate screen/tab/pane, reveal on desktop).

Goal

From a phone, tablet or laptop browser, a paired user sees the desktop's Workspaces, switches the desktop to one by tapping its card, browses its Worktree sections and tabs (with agent status dots), activates a tab (the desktop follows), sees live agent sessions ranked needs-input first, and watches all of it update in real time. The Terminal screen exists but shows "Live view arrives in the next phase".

Prerequisites

Phases 1–2. Read web-ui.html in full; it defines the file layout, store shape, layouts and components this phase creates.

Tasks

Task 1 — Navigation commands (Rust)

  • In commands.rs implement project.open, home.activate, screen.activate, tab.activate, pane.focus, desktop.reveal per protocol.html. Shared resolver helpers in app/src/remote_control/resolve.rs: window_for_screen(screen_id), workspace_for_screen(screen_id) -> ViewHandle<Workspace>, tab_index(workspace, tab_id), terminal_view(terminal_id) -> (window, ViewHandle<Workspace>, ViewHandle<PaneGroup>, PaneId, ViewHandle<TerminalView>), all via WorkspaceRegistry (never views_of_type). Ids parse from the D10 string format; failures → not_found.
  • project.open: if a window owns the project → that window's host open_project (activates its screen) else the active window (or the only window) → open_project; return the resulting screen_id. Both go through ViewHandle<ProjectHost>::update. Do not focus the OS window (the user may be at their desk with another app in front); desktop.reveal is the explicit "bring it forward".
  • tab.activate first activates the owning screen (ProjectHost::activate_screen by index from screen_ids_for_window) so the desktop shows what the phone shows, then ActivateTab.
  • Every mutation ends with mark_dirty (the observers will also fire; calling it explicitly guarantees a push even if a code path never notifies).
  • Unit tests in commands_tests.rs: a two-screen test host; screen.activate flips active_screen_index; tab.activate on a closed tab → not_found.

Task 2 — Vendoring and static structure

  • Add script/vendor_remote_control_assets (from web-ui.html), run it once, commit vendor/ with VERSIONS and licenses. The terminal is not used until Phase 4, but the shell already loads xterm.css/xterm.js so the asset pipeline is proven now.
  • Create the files listed in the guide: index.html (replace the placeholder), app.js, store.js, ws.js, router.js, dom.js, ui/layout.js, ui/workspaces.js, ui/workspace.js, ui/sessions.js, ui/terminal_view.js (placeholder), ui/sheets.js, styles.css, icons.svg. pair.html gets the same stylesheet.

Task 3 — Store, socket client, router

  • store.js: createStore(initial) → { get, patch(partial), subscribe(fn) }; selectors activeWindow, screenById, projectById, sessionsRanked, terminalById (index maps rebuilt on each state).
  • ws.js: connect({ onHello, onState, onEvent, onStatus }); command(name, params, opts) → Promise with timeout; sendBinary(attachId, bytes) and onBinary(attachId, handler) (used in Phase 4); heartbeat ping every 15 s; reconnect with jittered backoff; server.shutting_down → banner "Remote Control was turned off on the desktop" and stop reconnecting until the user taps Retry.
  • router.js: hash routes from the guide; navigate(name, params, {replace}); sheets push a history entry; back closes them.

Task 4 — Layouts and frame

Top bar (title, connection dot, overflow menu with "Settings" (client prefs, minimal now), "Log out"), content, bottom nav (phone) / side rail (desktop), toast stack, banner slot.
  • styles.css: tokens (dark default, light via media query and data-theme), reset, frame grid for the three breakpoints, safe-area padding, components (card, row, dot, pill, badge, sheet, menu, toast, banner, button, input). Touch targets ≥ 44 px.

Task 5 — Screens

  • Workspaces: Home card + project cards (name, kind glyph, branch, "N worktrees", working/needs-attention pills, "open" indicator, relative last-opened). Tap → project.open then #/w/<id>; Home → home.activate then #/w/home. If features.ade_workspaces is false, show only Home with an explanatory line.
  • Workspace detail: header (name, branch, "Show on desktop" → desktop.reveal of the active terminal if any, else screen.activate); sections → tab rows (icon by kind with status dot, title, pane count, pinned glyph, active highlight); pane list expands under a multi-pane tab. Tap tab → tab.activate; if the tab's focused pane is a terminal, also navigate to #/t/<terminal_id>. Kebabs are present but only "Show on desktop" is wired (Phase 6 fills the rest; render the other items disabled so layout is final).
  • Sessions: live sessions list from snapshot.sessions (ranked), each row with agent artwork (PNG via /assets/…/agent_icons/ when AgentIcon::Image, else a glyph), status pill, title, workspace · worktree, tool preview; tap → terminal route; secondary → desktop.reveal. History section placeholder ("Session history arrives later").
  • Terminal placeholder: header wired to state (title, mode badge), body text "Live view arrives in the next phase", back navigation.

Task 6 — Connection UX

  • Banner states: connecting, reconnecting (with countdown), server shut down, protocol mismatch ("Update Spirit or reload"), instance changed (toast "Spirit restarted", navigate to Workspaces).
  • Pending indicator on the tapped card/row until the next state arrives or the command errors (toast with the error message).

Out of scope

  • Terminal rendering and input (Phases 4–5); creation/deletion (Phase 6); history and alerts (Phase 7); Workspace creation (Phase 8); device management (Phase 9).
  • Drag-and-drop reordering, tab groups editing, multi-window juggling beyond showing all windows' screens.

Verification

  • ./script/presubmit green; git diff of JS/CSS contains no comments.
  • Laptop browser at 1280 px, 800 px and 390 px widths: the three layouts render, nothing overflows horizontally, all controls reachable.
  • iPhone Safari and Android Chrome over LAN (enable LAN access; use the machine's IP): pairing via the URL works; Workspaces → tap → desktop switches; tabs list matches the desktop's vertical tabs panel section by section; tap a tab → desktop activates it; Sessions shows a running Claude Code with its status; switching tabs on the desktop updates the phone within ~100 ms; airplane-mode toggle → reconnect banner then recovery; quit Spirit → "shut down" banner.
  • iPad Safari: two-column layout; sheets render as dialogs.
  • CSP: the browser console shows zero CSP violations; no request leaves the origin (Network tab).

Gotchas

  • Do not recreate the xterm container element on re-render even though nothing uses it yet — build the terminal screen's DOM once per route entry now so Phase 4 does not have to restructure the renderer.
  • project.open chooses a window. With two desktop windows and a project open in neither, use the active window; if none is active (app in background), the first window from window_ids(). Document this in the command's error-free path; never create a window from a command.
  • Agent icons are PNGs under app/assets/bundled/png/agent_icons/ only for some agents (AgentIcon::Image); others are glyphs. Map glyphs to the SVGs in app/assets/bundled/svg/ where the same icon exists; otherwise use a generic robot glyph. Do not ship a second copy of any asset — route the existing bundled files.
  • Hash routing and Safari: hashchange fires after popstate; use one handler. Sheets that push history must be closed on popstate without navigating twice.
  • Do not render with innerHTML from template strings containing app data — titles can contain < (commands like cat <file). dom.js's h() only ever sets textContent.
