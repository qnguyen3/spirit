Phase 8 — Workspace creation

Adding Workspaces from the web: register an existing folder (with a directory browser), clone a repository with live progress, create a new project, plus rename / remove / reveal — parity with the desktop's New Workspace modal and Overview.

Goal

From a tablet: tap "New Workspace" → choose Open folder (browse ~/code, pick api), Clone (paste a URL, pick the parent dir, watch the progress bar), or Create (name + parent) → the Workspace is registered and opened on the desktop and appears as a card; long-press a card → Rename / Reveal in Finder / Remove from Spirit (confirm).

Prerequisites

Phases 1–7. Requires FeatureFlag::AdeWorkspaces (the commands answer feature_disabled otherwise).

Context

  • Desktop flows: NewWorkspaceModal app/src/projects/new_workspace_modal.rs (modes Open/Clone/Create :38, events :63); host handlers app/src/projects/host.rs:876-891; register_and_open_folder(path, ctx) :782 → discover_repo_root + detect_primary_branch → finish_registering_folder :797-812 (registry + PersistedWorkspace::user_added_workspace + open_project); start_clone :919 (progress via git_ops::clone(url, parent, dir_name, path_env, progress, cancel) app/src/projects/git_ops.rs:597, clone_cancelled: Arc<AtomicBool> host.rs:131); start_create :977 (init_new_project git_ops.rs:531); derive_clone_directory_name git_ops.rs:296; remembered parents WorkspaceCreationSettings app/src/projects/settings.rs; ProjectHostAction::RemoveProject → RemoveWorkspaceDialog app/src/projects/remove_workspace_dialog.rs; overview events OverviewEvent::{RevealProject, StartRename…} app/src/projects/overview.rs:102, 361-376; registry rename_project/remove_project app/src/projects/registry.rs:214, 201.
  • Known issue to keep in mind: the 0828 closeout notes the desktop clone modal drains progress only at completion; the remote flow streams progress properly, and fixing the desktop path is a welcome side effect but not required.
  • Reveal: the desktop's reveal action (search RevealProject handling in host.rs:1010-1042) uses a platform "reveal in file manager" helper — reuse it.

Tasks

Task 1 — Headless registration/clone/create (refactor)

  • In host.rs extract from start_clone / start_create two pub(crate) functions with completion callbacks and a progress sink: 
    pub(crate) struct CloneJob { pub id: CloneJobId, pub cancelled: Arc<AtomicBool> }
pub(crate) fn clone_project(&mut self, url: String, parent: PathBuf, directory_name: Option<String>,
    on_progress: impl Fn(CloneProgress) + Send + 'static,
    on_done: impl FnOnce(&mut ProjectHost, Result<ProjectId, String>, &mut ViewContext<ProjectHost>) + 'static,
    ctx) -> CloneJob
pub(crate) fn create_project(&mut self, name: String, parent: PathBuf, on_done: …, ctx)
pub(crate) fn register_folder(&mut self, path: PathBuf, on_done: …, ctx)
    The modal's handlers become callers whose callbacks drive the modal UI (progress bar, close, error). Multiple concurrent clone jobs are allowed (the modal only ever runs one; the bridge may run several — keep a HashMap<CloneJobId, CloneJob> on the bridge).

Task 2 — Commands (Rust)

  • project.register {path}: canonicalize, must be an existing directory (else not_found); deferred through register_folder on the active window's host; reply {project_id}.
  • project.clone {url, parent, directory_name?}: deferred; the single result arrives when the clone finishes (or fails / is cancelled). Progress is streamed as event project.clone_progress {job_id, phase, percent, message} where job_id equals the command id, so the client correlates without a second round trip. project.clone_cancel {job_id} flips the job's cancel flag; the deferred result then reports error conflict with message "Clone cancelled". Persist last_clone_parent like the modal does.
  • project.create {name, parent}: deferred; persist last_create_parent.
  • project.rename {project_id, name}, project.remove {project_id, confirm} (close its screens via close_project_screen in every window that has one, then remove_project — mirror RemoveWorkspaceDialog's confirm path, without the dialog), project.reveal {project_id}.
  • fs.list_dirs {path?, include_hidden?}: deferred to the background executor; path defaults to the home dir; returns sorted directory entries (name, absolute path, is_git_repo = has a .git entry), the parent path, and suggested: [last_clone_parent, last_create_parent, ~/code-like dirs that exist]. Reject non-directories with not_found; cap 2000 entries; never follow the request into files. Also fs.suggest_parents is folded into the same response.
  • Tests: fs.list_dirs on a temp tree; project.register on a non-directory → not_found; project.remove without confirm → invalid_request.

Task 3 — Web UI

  • "New Workspace" card/button → sheet with three tabs: Open folder (directory picker → Register), Clone (URL, parent via picker with the suggested list, derived directory name shown and editable, Clone → progress bar with phase label and Cancel), Create (name, parent via picker, Create). On success: navigate to the new Workspace's detail.
  • ui/dirpicker.js: breadcrumb (tap to go up), list with folder glyphs and a git badge, "Use this folder", hidden toggle, path text field for typing/pasting an absolute path (validated by fs.list_dirs).
  • Card context menu: Rename (sheet), Reveal on desktop, Remove from Spirit (confirm sheet with the desktop's copy: it never deletes files).
  • Overview parity: card shows the branch, worktree count, open indicator, agent counters (already), plus last-opened; MRU order is the server's.

Out of scope

  • File browsing beyond directories, file contents, uploads. Native folder pickers (impossible from a remote browser). Multi-host projects. Deleting worktree folders when removing a project (the desktop does not either).

Verification

  • ./script/presubmit green; desktop New Workspace modal unchanged in behavior (open/clone-with-cancel/create all re-tested by hand).
  • Tablet: register ~/code/spirit → card appears, desktop opens it; register the same folder again → focuses the existing (D13 of the 0828 spec); clone a small public repo with progress ticking (phases: counting/compressing/receiving/resolving) and a working Cancel; create "scratch" in ~/tmp → a git repo with an initial commit; rename, reveal, remove.
  • Directory picker handles a 1500-entry directory smoothly and refuses /etc/passwd.

Gotchas

  • Clone progress callbacks run on a background thread; forward them to the bridge with a bounded channel + spawn_stream_local (precedent crates/watcher/src/lib.rs:155-185), then to the client channel. Throttle to 10 events/s.
  • Interactive PATH for git: every git call passes interactive_path_env (the modal does); the headless functions must too, or LFS/credential helpers fail in the GUI's environment.
  • PersistedWorkspace::user_added_workspace must stay in the pipeline (it feeds LSP/repo-metadata indexing); the refactor keeps finish_registering_folder as the single sink.
  • Which window? Registration opens the project in the active window (or the only one); a project already open elsewhere focuses that window (D11).
